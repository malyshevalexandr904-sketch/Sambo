## Изменения 0.13.1

Исправления по независимому ревью 0.13.0 (2026-10-17): high — нет, medium — 3, low — 13; исправлены все, кроме одного: время ответа `verify-email/resend` для существующего неподтверждённого адреса по-прежнему отличается от неизвестного (как у восстановления пароля) — в известных ограничениях. Второй проход ревью по исправлениям (2026-10-18): high — нет, medium — 1 (кнопка возврата роли на планшете перезагружала страницу и упиралась в «Покинуть страницу?»), low — 5; исправлены.

- **Федерация и турнир:** `TOURNAMENT_MANAGER`, выданный создателю, действует в роли «Персонал турнира»; у `FEDERATION_ADMIN` в роли руководителя прав управления турниром нет (у `ORGANIZER` — есть наследованием). После создания турнира без полномочий управления в текущей роли сессия переходит в «Персонал турнира» (`selectIfHeld`).
- **`session_role.rev`** (миграция `20261017120000_session_role_rev`): версия записи; автоматическая проверка пишет только при неизменной версии (раньше — сравнение `updated_at`). `state()` не перезаписывает выбор, сделанный в соседнем запросе. `selectIfHeld` не превращает сбой в ошибку уже выполненного действия.
- **Живые данные:** `PUT /me/role` публикует `{"type":"session-role","sessionId"}` в Redis `sde:live:control`; узлы api отправляют соединениям этой сессии `expired` (служебные подписки сняты, клиент подключается заново с новой ролью).
- **Импорт:** `GET /athletes/imports/{id}` и скачивание исходного файла (`IMPORT`) — только создателю с `athlete.import` в организации задания в выбранной роли.
- **Судейство:** `myRoles` (планшет, «Судейство») — только в роли кабинета, где у пользователя есть роль бригады этого турнира (`CREW_CANDIDATE_ROLES`: судья, главный судья — «Судья»; секретарь — «Персонал турнира»). Планшет: отказ 403/404, если роль сессии изменилась с открытия планшета, не сбрасывает очередь, а ставит её на паузу; возврат роли — кнопкой без перезагрузки или в другой вкладке — продолжает отправку.
- **Повторный выбор той же роли** (`PUT /me/role`) ничего не меняет и живые соединения не трогает; шлюз находит соединения сессии по индексу, а не перебором всех.
- **Повторное письмо:** не гасит прежние ссылки; подтверждение гасит все ссылки пользователя. `email-delivery`: без `SMTP_HOST` — `localhost` (письма не покидают сервер).
- **Веб:** переключатель — кнопки (`aria-pressed`, группа с подписью); на экранах без меню — строка роли; после действий, меняющих роль на сервере, — сброс данных запросов (`resetQueries`) и оповещение вкладок (`tabId`, своя вкладка сообщение игнорирует), живое соединение переподключается по `expired` от сервера. Кнопка повторного письма ждёт столько, сколько сказал сервер (`retryAfterSeconds`).

## Изменения 0.13.0

Пакет правок заказчика по Phase 9a (2026-10-17): первый экран и название «Digital Sambo», регистрация с выбором роли, повторное письмо подтверждения, документы у каждой роли, **роль в кабинете** — человек с несколькими ролями работает в одной выбранной, и права на сервере действуют только для неё. Ответы заказчика: название заменить везде; почта подтверждается до анкеты; документы — PDF или фото; права зависят от выбранной роли.

### PERMISSIONS.md — роль в кабинете

| Роль кабинета | Роли доступа и связи, которые в ней действуют |
|---|---|
| `ADMIN` — администратор платформы | `SUPER_ADMIN`, `PLATFORM_ADMIN` (как и раньше, только с TOTP) |
| `ORGANIZATION_HEAD` — руководитель организации | `FEDERATION_ADMIN`, `ORGANIZER`, `CLUB_MANAGER` (роль руководителя по типу организации, Phase 9a) |
| `TOURNAMENT_STAFF` — персонал турнира | `TOURNAMENT_MANAGER`, `SECRETARY` |
| `REFEREE` — судья | `CHIEF_REFEREE`, `REFEREE`; роль есть и у судьи без назначения (профиль судьи) |
| `MEDICAL` — врач турнира | `MEDICAL_STAFF` |
| `COACH` — тренер | `COACH`; профиль тренера (политика `COACH_OWN`, «мои спортсмены», заявка по умолчанию, проверка заявок спортсменов) — только в этой роли |
| `ATHLETE` — спортсмен | связь `SELF` (свой профиль, свои документы, согласия, QR участия) |
| `GUARDIAN` — представитель спортсмена | связь `GUARDIAN` (дети, их документы и согласия); роль есть и у ещё не подтверждённой связи |

- Каждая роль доступа — ровно в одной роли кабинета (`CABINET_ROLE_GRANTS`, тест контрактов). Права считаются прежним алгоритмом (раздел 6) по **отфильтрованному** набору: `PolicyService.grants` = `grantsForRole(effectiveGrants, activeRole)`; организации и турниры, где у пользователя нет ролей выбранной роли кабинета, выпадают целиком (их служебные данные в этой роли не видны — 404). Кэш эффективных прав — полный, фильтр — на каждый запрос. Связи `SELF` и `GUARDIAN` проверяются только в своей роли (`relationActive`), профиль тренера — только в роли «Тренер» (`coachIdOfUser`).
- Без ролей (`activeRole = null`) действует только то, что не требует роли: свой профиль, уведомления и подписки, заявка на роль (`/onboarding`), опубликованные турниры и публичный API.
- **Выбор — на сессию входа** (семейство refresh token): планшет судьи и телефон того же человека в роли представителя не мешают друг другу. Новая сессия начинается с последней выбранной роли (`user.preferred_role`), если она есть у пользователя, иначе — с первой по порядку `CABINET_ROLES`. При изменении прав (`permissionsVersion`) выбор проверяется: роль остаётся, если она есть, иначе — роль по умолчанию; так пользователь, которому одобрили заявку, не перезаходит.
- Сессия сама переходит в полученную роль, когда пользователь в том же действии её получает: принял приглашение в организацию или персонал турнира, приглашение представителя, создал организацию без полномочий (стал руководителем).
- Уведомления (лента, письма, push) приходят по всем ролям: получатель не зависит от выбранной роли. Но подробности в ленте (имя спортсмена, данные заявки) показываются по правам выбранной роли — как и сами экраны. Если ссылка ведёт в раздел другой роли, экран «не найдено / нет доступа» предлагает открыть его в нужной роли.
- WebSocket: права канала проверяются по роли сессии при подписке; после переключения веб перезагружает страницу (новое соединение), другие вкладки браузера получают предупреждение (`BroadcastChannel`).

### Веб

- Первый экран: логотип, «Digital Sambo», «Единая цифровая экосистема самбо»; ссылки «Перейти в кабинет» нет — вошедшему кнопка карточки входа открывает кабинет; «Турниры» → «Продолжить».

### Сценарии и переходы

- **Куда уходит заявка:** тренер или спортсмен, выбравший организацию, и присоединение к организации — `PENDING_ORGANIZATION_APPROVAL` (руководитель организации; федерация — и дочерних; тренер спортсмена — если ему дано право); остальное — `PENDING_REVIEW` (платформа). Платформенные роли с правом проверки решают и заявки организаций — для поддержки.
- **Кто что может:** заявитель — изменить черновик или возвращённую заявку, приложить и удалить документы, отправить, отменить незавершённую. Проверяющий — одобрить, отклонить (причина обязательна), вернуть на исправление (причина обязательна). Свою заявку не решает никто. Переходы — `domain/onboarding-rules.ts`, статус меняется только с проверкой версии и текущего статуса (`If-Match`): двойная отправка или два решения одновременно — `INVALID_TRANSITION` / `VERSION_CONFLICT`.
- **Полнота заявки** — одна функция для формы и сервера (`contracts: onboardingProblems`): обязательные поля по роли и ответам, возраст (руководитель и тренер — от 18, судья — от 14, спортсмен — от 5 до 25), Telegram при выборе этого способа, реквизиты российского юрлица, документы по правилам. Сервер дополнительно проверяет, что организация активна и подходит для выбора, тренер работает в ней и подтверждён (членство с ролью «Тренер»), категория и регион существуют, организация ещё не зарегистрирована.
- **Одобрение** (одна транзакция): запись «человек» заявителя (новая или обновлённая данными заявки; возможные дубли — показываются проверяющему, слияние — прежним инструментом платформы); руководителю — организация `ACTIVE` с реквизитами и роль по типу (`CLUB_MANAGER`, `FEDERATION_ADMIN`, `ORGANIZER`); тренеру — профиль, а с организацией — работа в ней и членство «Тренер»; спортсмену — профиль, а с организацией — основной клуб и основной тренер (смена клуба или тренера закрывает прежние днём раньше, история периодов остаётся); судье — профиль с категорией (у существующего профиля категория повышается). Тренер к моменту одобрения ушёл из клуба или организация приостановлена — `TRANSITION_PRECONDITIONS_NOT_MET` / `ORGANIZATION_NOT_ACTIVE`.
- **Дубли организаций:** тот же ИНН или то же название после нормализации (регистр, «ё», кавычки, организационно-правовая форма в начале) среди организаций и незавершённых заявок руководителей — `ORGANIZATION_ALREADY_REGISTERED` (409) при отправке и при одобрении. Организация по введённому названию сама не создаётся.
- **Присоединение позже** (`JOIN_ORGANIZATION`): тренер или спортсмен с одобренным профилем выбирает организацию (и тренера); личные данные и документы повторно не нужны. Повторная первичная регистрация той же роли — `ALREADY_EXISTS`.
- **Отличие от ТЗ (шаги):** роль выбирается в кабинете (создаётся черновик), вопросы сценария — шаг 2, далее данные, документы, способы связи, проверка и согласие, отправка, статус. Вход и подтверждение email — до мастера: заявка хранится на сервере и принадлежит учётной записи.

### ARCHITECTURE.md

- Модуль `onboarding` (api): `domain/onboarding-rules.ts` (переходы, нормализация названия), `application/` — заявитель (`OnboardingService`), переходы и очередь (`OnboardingWorkflowService`), доступ (`OnboardingAccessService`), последствия одобрения (`OnboardingApprovalService`). ### Правило «скоро»

- Очередь ковра — как у планшета (7a): вызванные и идущие схватки впереди всех; ждущие пары с другого ковра ковёр не держат и в счёт не идут; схватка с неизвестной парой, со снятым участником или уже вызванная не объявляется; плановое начало — не позже чем через 2 часа. «Впереди не больше N» — считая идущую и вызванные.
- Получатели спортсмена: подтверждённые действующие представители, сам спортсмен с учётной записью, подписавшиеся — пока подписавшийся действующий член клуба, подавшего заявку спортсмена, с правом подавать заявки (тренер, руководитель). Пользователь заблокирован или удалён — не получает. Получивший доступ позже (подписался, вернулся в клуб), пока схватка ещё впереди, получает своё «скоро».
- **Отличие от плана:** подписаться может любой, кто видит карточку спортсмена, но уведомления по подписке получают только тренеры и руководители клуба заявки — подсказка у кнопки.
- «Изменилось время» сравнивает место схватки с местом до этой правки: несколько мелких правок подряд (по 5–9 минут) могут сдвинуть схватку больше чем на 10 минут без уведомления — «скоро» всё равно придёт по очереди ковра.
- Сводка клубу копит правки, пока её задача ждёт 10 минут; правка, пришедшая в те секунды, когда сводка уже отправляется, в неё не попадает — сводка общая («расписание изменилось»), клуб видит текущее расписание.

### SECURITY.md

- **В push и письмах — без имён детей** (экран блокировки): заголовок вида, ковёр, номер схватки, время, турнир. Имя — только в ленте приложения, пока пользователь видит карточку.
- **Адрес push-службы прислал браузер — защита от SSRF:** api принимает только `https://` на порту 443, без учётных данных, имя хоста с точкой — не IP-адрес, не `localhost`, не `.local`; worker при соединении проверяет каждый адрес, в который разрешилось имя (частные, локальные, служебные IPv4 и IPv6, 6to4, Teredo, NAT64 — отказ), перенаправления не выполняет, таймаут 10 с. Ключ устройства, которым нельзя зашифровать, — подписка удаляется.
- Сообщение push шифруется ключами устройства (RFC 8291, aes128gcm), запрос подписан VAPID (RFC 8292, ES256); TTL — 1 час для уведомлений дня соревнований (устарели — не показываются), 24 часа — для остальных; метка (`Topic`) — новое «скоро» по той же схватке заменяет недоставленное.
- Устройство не перехватывается тихо: приложение при открытии привязывает к новой сессии только своё устройство (`onlyIfMine`); выход снимает подписку своего устройства, чужую (общий планшет) не трогает.
- Отзыв сессии (выход, смена пароля, отзыв, повтор refresh token) сначала блокирует строки семейства токенов, затем отзывает их отдельной командой: выход больше не проигрывает одновременному обновлению сессии в соседней вкладке (иначе новый токен оставался неотозванным).
- Ключи VAPID проверяются при запуске: неверная пара или контакт (`WEB_PUSH_SUBJECT` — `mailto:` с адресом или `https://` с хостом) — push выключен целиком; ошибка настройки при отправке устройства не удаляет.
- Service worker `/sw.js`: показывает уведомление и открывает только адрес своего сайта (проверяется разобранный адрес); вкладку с этой страницей — фокусирует, иначе — новое окно. CSP: `worker-src 'self'`, `manifest-src 'self'` (`'strict-dynamic'` в `script-src` не разрешает `'self'` для воркеров).

### API.md, 7 — протокол

- Socket.IO, путь `/ws` (без завершающей косой черты), пространство имён `/live`; сначала WebSocket, при неудаче — long polling. Вход — cookie `sde_at` **только с Origin `APP_URL` или `CORS_ORIGINS`** (с другого Origin — как без входа; без Origin браузер WebSocket не открывает, cookie — SameSite=Lax) или `auth.token` (Bearer). Отказ в рукопожатии (сбой БД или Redis при проверке входа, больше 1000 соединений с адреса) клиент повторяет сам с нарастающей паузой.
- Сообщения клиента: `subscribe { channel, lastSeq? }` → `{ ok: true, seq, snapshot }` | `{ ok: false, error: { code } }`; `unsubscribe { channel }` → `{ ok }`; `ping { clientTime }` → `{ serverTime }`. Сообщение сервера `expired` — срок access token истёк: служебные подписки сняты, клиент обновляет сессию и подключается снова. Коды отказа: `UNAUTHENTICATED`, `TOKEN_EXPIRED`, `FORBIDDEN`, `NOT_FOUND` (канала нет или турнир не опубликован), `VALIDATION_FAILED` (неизвестное имя канала), `RATE_LIMITED`, `INTERNAL_ERROR`. Лимиты: 50 подписок на соединение, 20 запросов клиента в секунду, сообщение до 16 КБ, 1000 соединений с одного адреса на узел `api` (ограничение злоупотреблений; зрители в одной сети — пересмотреть в Phase 9). Подписка и отписка одного канала выполняются по очереди: отписка, отправленная, пока подписка ещё проверяется, побеждает. Номер ковра в имени канала — без ведущих нулей (`public:mat:{slug}:1`, не `…:01`).
- **Каналы:** + `ops:mat:{id}` (изменения ковра: очередь, текущая схватка, счёт — планшет и экран «Ковры»). Каналы состояния — `public:mat:{slug}:{номер}` (`mat.state`, `PublicMatStateDto`: текущая схватка — идёт или вызвана, последняя завершённая за час, следующая пара) и `public:match:{publicId}` (`match.state`, `LiveMatchDto`); снимок — последнее состояние. Каналы изменений — `ops:competition:{id}`, `ops:mat:{id}`, `ops:match:{id}`, `public:competition:{slug}` (`changed`: `{ topics, categoryIds, matIds, matchIds }`, темы — `LIVE_TOPICS`) и `user` (`notification`: `{ notificationId, type }`) — клиент перечитывает данные по REST. Оценка (изменение только счёта) в `ops:competition` не приходит.
- **Отличия от API.md, 7:** `seq` — счётчик Redis у каждого канала, в том числе у схватки (не `Match.stateSeq`: у схватки два канала, у ковра — несколько схваток). Пропущенные сообщения не досылаются списком (`events` в ответе не используется): каналы состояния отдают снимок, каналы изменений — признак «перечитать». Канал `user` раздаётся в комнату `user:{id}` — клиент другого пользователя в неё не попадает.
- Публичная проекция табло (ADR-15): «Фамилия И.» — только при действующем согласии на распространение ПДн (общем или на этот турнир), иначе `name: null, hidden: true` и табло показывает угол; клуб, регион. Ни идентификаторов участий и спортсменов, ни полного имени. Время — по часам сервера: `clock` — «значение + момент», удержание — момент начала.

### ARCHITECTURE.md, 13 — Realtime

- Модуль `live` (шлюз, права на каналы, лента изменений, публикация) над `auth` (`AccessTokenAuthenticator` — проверка access token, общая для `AuthGuard` и шлюза), `competitions`, `refereeing` (`ScoreboardService` — публичная проекция ковра и схватки; она же — публичный снимок табло в модуле `public`). Домены о шлюзе не знают.
- **Отличие:** use case не вызывает `RealtimePublisher` после commit — изменения приходят лентой из PostgreSQL (`pg_notify` на `sync_log`). Так в живые каналы попадает любое изменение операционных данных турнира, кем бы оно ни было записано (команда, автоматические неявки, worker, seed), и только после commit. Ведущий узел `api` (блокировка в Redis с продлением) слушает ленту, собирает изменения пачками (40 мс), строит проекции и публикует; узлов `api` может быть несколько — рассылают сообщения все. Соединение прослушивания проверяется запросом при каждом продлении блокировки (и TCP keepalive): ошибка или два ответа подряд дольше 5 с («тихий» обрыв) снимают роль ведущего; не удалось продлить — публикация прекращается сразу (двух ведущих не бывает). Новый ведущий — в том числе тот же узел после восстановления связи — **пересинхронизирует** действующие турниры (закрыта регистрация … идут соревнования): служебные каналы турнира — «изменилось всё», ковров — «изменилось», табло — состояние ковров и идущих схваток заново; так экраны получают изменения, записанные, пока ленту никто не слушал. Пересинхронизация — не чаще раза в 30 с, после идущей публикации пачки, а изменения, пришедшие во время неё, публикуются следом (сохранённый снимок не старее опубликованного). Табло сравнивает время расчёта состояний — часы узлов `api` должны быть синхронизированы (NTP). Сбой проекции одного ковра или схватки не мешает остальным каналам пачки; публичное состояние схватки пересчитывается, только пока на неё смотрят (вызвана, идёт, на паузе, завершена в последний час).
- `RealtimePublisher` — `LivePublisher` в `packages/server-kit`, общий для `api` и `worker` (уведомления): один скрипт Redis выдаёт `seq`, сохраняет последнее состояние и рассылает сообщение узлам через pub/sub — порядок сообщений канала совпадает с `seq`. Redis adapter Socket.IO не нужен: каждый узел подписан на `sde:live` и раздаёт сообщения своим подписчикам.
- Изменение только счёта отличается от изменения статуса по версии схватки: событие журнала версию не меняет. Публичное состояние табло пересчитывается по журналу с моментами, сведёнными к часам сервера (сдвиг устройства — наименьшая разница «приём сервером − время устройства» по его событиям), — расхождение часов планшета и табло таймер не сдвигает. Табло отбрасывает состояние схватки старше показанного (версия, номер события).
- Web: одно соединение на вкладку (ленивое — при первой подписке), подписки по каналам с `seq`; пока подписка подтверждается, сообщения копятся; пропуск или сброс счётчика — повторная подписка с `lastSeq`. Сообщения каналов изменений складываются за 250 мс и обновляют запросы TanStack Query (перечитываются только открытые экраны) — по темам: взвешивание обновляет карточку турнира и разделы взвешивания и допуска, а не «Судейство»; изменения турнира и участий — всё. Здоровье считается **по каналу экрана**: запасной опрос — раз в минуту, пока канал работает, прежний интервал — если связи нет или подписка отклонена; временный отказ (сбой, лимит) повторяется с паузой до минуты, «нет прав» и «не найдено» — после переподключения. На планшете и экране «Ковры» — отметка «Обновление раз в 5 с», если канала ковра нет, а REST работает. Транспорт — WebSocket, при неудаче — long polling (`tryAllTransports`). Выход и вход закрывают соединение (оно не переживает смену пользователя во вкладке).
- **Обновление сессии согласовано между вкладками:** ротация refresh token строгая (повтор старого токена отзывает сессию), а истёкший access token шлюз отмечает во всех соединениях одновременно. Обновление идёт под блокировкой браузера (Web Locks API, `sde-session-refresh`), и внутри неё сначала проверяется `GET /me` — если другая вкладка уже обновила сессию, повторного обновления нет; запросы под блокировкой — не дольше 10 с. Без Web Locks (страница не по HTTPS, старый браузер) — случайная пауза до 3 с перед проверкой. Так же — для запросов REST, получивших 401.
- Остановка: шлюз и лента останавливаются в `onModuleDestroy` — до отключения Prisma (хуки уничтожения идут в обратном порядке инициализации).
- **Известное ограничение (масштаб):** PostgreSQL сериализует commit транзакций, вызвавших `NOTIFY` (общая блокировка очереди уведомлений), — каждая запись в операционные таблицы турнира теперь уведомляет. Для клубных и региональных турниров (единицы команд в секунду) это незаметно; нагрузочный тест 8b (12 ковров) проверит запас, при необходимости — одно уведомление на транзакцию или чтение `sync_log` по номеру вместо `NOTIFY`.
- Табло ковра — страница `/scoreboard/mat/{id}` без входа: во весь экран, 1080p и 4K (размеры — от высоты и ширины экрана), экран не гаснет (Wake Lock), без живого соединения — опрос снимка каждые 5 с.

### SECURITY.md

- **Подключение чужого сайта к служебным каналам (CSWSH):** cookie входа принимается только с разрешённого Origin; с другого — соединение анонимное. Bearer — только в `auth.token` рукопожатия.
- **Отзыв сессии и права:** при подключении и при каждой подписке на служебный канал сессия и пользователь перечитываются (отозвана, заблокирован — соединение становится анонимным, служебные подписки снимаются), права — по текущей версии прав пользователя (снятая должность в турнире действует сразу, как в REST); при истечении access token служебные подписки снимаются. Уже открытая подписка после отзыва сессии или снятия прав живёт не дольше 15 минут (срок access token); новые подписки и запросы REST отклоняются сразу.
- Команды по WebSocket не принимаются; лимиты подписок, частоты и размера сообщений; в сообщениях — только идентификаторы и публичная проекция.
- Письмо «опубликованы результаты» — без имён детей и мест (только турнир и категория), подробности — в приложении после входа.

### PERMISSIONS.md

- Новых прав нет: `result.publish`, `result.amend`, `match.create`, `match.cancel`, `medical.record`, `medical.view`, `export.create` — в матрице с Phase 1. Изменяет подтверждённый результат только главный судья; публикуют главный судья, руководитель турнира и организатор; ручную схватку добавляют секретарь, руководитель турнира и организатор, отменяют — главный судья, руководитель турнира и организатор.
- Заметка врача — только `medical.view` (врач турнира): в схватке, протоколе, аудите и событиях её нет.
- История спортсмена — по доступу к карточке (`AthleteAccessService.assertView`): клуб, тренер, представитель, сам спортсмен; чужие — 404. Слияние дублей спортсменов переносит историю к оставшемуся профилю (как и участия).
- Изменение результата и запись врача проверяют право и в сервисе — в аудит пишется вмешательство платформы (`platformIntervention`), как у остальных команд.

### ARCHITECTURE.md

- Модуль `results` (итоги категории, публикация, запросы итогов и истории, проверка завершения турнира через `CompetitionExtensions`) над `brackets` (места формата — `BracketsService.standing`), `categories`, `competitions`, `athletes`. Команды судейства (`refereeing`) вызывают `CategoryResultsService.refresh` в своих транзакциях после продвижения сетки — после подтверждения, автоматических неявок и изменения результата.
- **Порядок блокировок** тот же, что в 7a: право записи `FOR SHARE` → турнир (только автоматический переход) → категория → жеребьёвка → схватка → заявка → участие. Публикация берёт категорию первой; изменение результата — категорию, жеребьёвку, схватку; снятие врачом — категорию, схватку, затем заявку и участие (`EntryWithdrawalService.withdrawBySystem`). Гонка «подтверждение последней схватки ↔ изменение другой» проверена в e2e (`Promise.all`).
- **Завершение категории:** сетка решена целиком (исход каждой схватки — подтверждённый, включая «без соперника» и автоматические неявки) — категория `→ COMPLETED` (из `DRAWN` — через `IN_PROGRESS`) в той же транзакции, места пишутся в `Placement`. Изменение результата, открывшее новые схватки, возвращает неопубликованную категорию в `IN_PROGRESS`: места снимаются, строка итогов остаётся и её версия растёт — публикация по итогам, которые видели до изменения, получит `VERSION_CONFLICT`, даже когда категория снова завершится. Опубликованную категорию так менять нельзя (`results_published_bracket_reopens`).
- **Места:** правило Q-13 стратегий формата 5a; в выбывании — нижние границы по кругу вылета (`2^(rounds−r)+1`), в утешительных — только медальные места (финал подгруппы — 3-е); снятый участник сохраняет достигнутое место (финалист, не вышедший на финал, — 2-е), двойного золота нет, если сняты оба финалиста. Неразрешимое равенство в круговой (цикл побед при равном счёте) — общее место и одинаковая медаль.
- **Изменение результата:** схватки узлов сетки блокируются (`FOR UPDATE`, по id) до проверки — вызов, старт или неявка бригады не проскочат между проверкой и приведением сторон. Исходы системы в зависимых схватках (автоматическая неявка, «без соперника») сбрасываются и пересчитываются, пока сетка не придёт в равновесие (≤ 64 проходов); у опубликованной категории пересчитанные исходы сразу публикуются. Схватки, где боролись или исход внесла бригада, — `DEPENDENT_MATCHES_STARTED` со списком. Изменивший результат становится подтвердившим.
- **Снятие врачом** завершает схватку, поэтому требует остановленного времени (как запись результата бригадой: сначала «Стоп» на планшете). Снимает участие только в этой категории (не во всех категориях турнира): иначе команда держала бы блокировки нескольких категорий; снятый сохраняет достигнутое место. В ручной схватке вне сетки участие не снимается — она на места не влияет.
- **Ручная схватка:** место в конце ковра сессии (`ScheduleAppendService`, модуль расписания); на места не влияет; после итогов категории тоже возможна (показательная, переигровка).
- **Протоколы:** данные — JSON с сервера, лист A4 книжный — страница веб-приложения с print CSS по согласованным макетам; номер листа — в поле страницы («Лист 1 из 1»), PDF — Phase 11.
- Экраны: вкладка турнира «Итоги» (с этапа жеребьёвки), места под опубликованной сеткой, «Результаты» в карточке спортсмена, страница схватки (`/referee/{competitionId}/matches/{matchId}`: результат, прежние варианты, изменение, перенос, отмена, врач), ручная схватка (`/referee/{competitionId}/matches/new`), протоколы (`/protocols/matches/{id}`, `/protocols/categories/{id}`), на планшете — «Отложить схватку» и отметка «Врач на ковре». Опрос: итоги — 15 с, страница идущей схватки — 5 с (мгновенное обновление — Phase 8).

## Изменения Phase 7a

Схватка на планшете ковра от вызова до подтверждённого результата: состояния схватки, журнал событий только на дополнение, счёт — чистая функция журнала и правил турнира (общий редьюсер сервера и планшета, тесты property-based), предварительный результат бригады и подтверждение руководителем ковра или главным судьёй с продвижением сетки, автоматические неявки снятых участников, результат «без соперника» системой, реальные статусы на экране «Ковры» и в сетке, раздел «Судейство». Ниже — уточнения, найденные при реализации; согласованную архитектуру они не меняют.

Главный судья и руководитель турнира — по прямым правам матрицы. Судья без назначения — 403.

### ARCHITECTURE.md

- Модуль `refereeing` (команды и запросы судейства, домен — машина состояний схватки) над `matches` (хранение агрегата схватки: схватка, стороны, журнал, результат — `MatchStoreService`), `brackets`, `scheduling`, `registrations`, `competitions`, `categories`. Редьюсер счёта — в `packages/contracts/src/scoring.ts`: тот же код на сервере (строгая проверка новой команды) и на планшете (предпросмотр до подтверждения).
- **Порядок блокировок:** право записи `FOR SHARE` → турнир `FOR UPDATE` (только когда первая схватка или первый подтверждённый результат переводит турнир `SCHEDULED → IN_PROGRESS`, `CompetitionStatusWriter.startOnFirstMatch`) → категория (`CategoryWorkflowService.lockForCommand`) → жеребьёвка (`BracketsService.lockDrawOfMatch`) → схватка `FOR UPDATE` → advisory-блокировка спортсмена в турнире → участие (условное обновление). Снятие участника берёт категорию до участия, а участие — до жеребьёвки: ни одна команда не держит схватку, ожидая участие той же категории, поэтому цикла нет (проверено независимой проверкой и гонками в e2e).
- Снятие участника → в той же транзакции подписчик события `registration.entry_withdrawn` (outbox) решает неявкой оставшиеся схватки, где соперник известен, по цепочке до неподвижной точки (≤ 64 проходов), включая утешительные; то же — после каждого подтверждения. Снятие спортсмена, который на ковре, запрещено (`athlete_in_active_match`) — исход фиксирует бригада.
- Автоматическая неявка (исход системы) не мешает новой версии жеребьёвки: «начатыми и сыгранными» для замены жеребьёвки считаются только схватки, где боролись или исход внесла бригада.
- Первая схватка категории переводит её `DRAWN → IN_PROGRESS`; то же — первый подтверждённый результат без старта (неявка по вызову). Автоматическая неявка статусы турнира и категории не меняет (снятие до соревнований не начинает их) — завершение категории, где все схватки решены автоматически, учитывается в 7b.
- Сущности, которые 7a трогает, но меняет 7b: изменение подтверждённого результата (`AMENDED`, ревизии), публикация (`PUBLISHED`), места и медали.
- Планшет: очередь команд с ключом идемпотентности и `expectedSeq` (фиксируется при первой отправке), повтор с тем же ключом при обрыве связи (пауза до 10 с), неотправленные команды переживают перезагрузку страницы (хранилище вкладки), конфликт со вторым планшетом — сброс очереди и перезагрузка журнала. Время чужого планшета сводится к своим часам по времени сервера; автоматический «Стоп» на длительности и конец удержания на верхнем пороге шлёт планшет, запустивший время (остальные — с запасом 3 с). Опрос: планшет — 5 с, раздел «Судейство» и подтверждения — 10 с, экран «Ковры» — 15 с (мгновенное обновление — Phase 8).

- **Когда:** турнир на этапе `DRAWING`, `SCHEDULED` или `IN_PROGRESS` (многодневный турнир тянет категории следующих дней); категория — `READY_FOR_DRAW`. Участники — одобренные участия с допуском `ADMITTED`; не допущенные в жеребьёвку не попадают.
- **Формат:** из запроса, иначе `formatOverride` категории, иначе `formatSelection` закреплённых правил по числу участников. Формат 5b — `format_not_available` с предлагаемым форматом в `details.suggested`.
- **Команда** участника для разведения — организация представительства, иначе клуб из снимка участия, иначе организация заявки; **регион** — представительства или из снимка.
- **Устаревший черновик:** допущенные участники или их команды изменились после жеребьёвки — хеш текущего входа не совпадает; черновик виден со `stale: true`, публикация — `draw_input_changed`.
- **Жеребьёвка — только по решённому допуску** (ARCHITECTURE.md, 16.2): если после готовности категории допуск кого-то снова не решён (документ вернули на проверку, отменили исключение), черновик не создаётся и не публикуется — `admission_pending`. Иначе спортсмен молча выпал бы из сетки.
- **Опубликовать можно только последний черновик категории** (`newer_draft_exists`): выбрать «удобную» сетку из нескольких черновиков нельзя, а каждая попытка остаётся в списке версий со своим номером. seed, заданный вручную, помечается (`manualSeed`) в версии, в аудите и на экране.
- `supersede` требует If-Match по общему правилу 1.4 (переход статуса версионируемого ресурса). Категория возвращается в `READY_FOR_DRAW` с той же проверкой, что и при переходе к жеребьёвке: допуск всех одобренных участий решён (иначе `admission_pending`).
- Турнир `DRAWING → CHECK_IN` — `TRANSITION_PRECONDITIONS_NOT_MET` (`draws_published`), пока в турнире есть опубликованная жеребьёвка.
- Номера схваток — сквозные в турнире, в порядке: основная сетка по кругам, утешительные, финал последним; параллельные публикации одного турнира нумеруются по очереди. Выданный номер не меняется при продвижении: схватка, оставшаяся без соперника, сохраняет номер (в сетке — «без схватки»), по нему работают печатная сетка и расписание. Номера удалённых при новой версии схваток могут освободиться; Phase 6 может перенумеровать схватки по расписанию.
- Длительность схватки — из правил по младшему возрасту категории, утешительные — `repechageMatchSeconds`, но не дольше основной схватки этого возраста.
- **Движок продвижения** для Phase 7: `BracketsService.applyConfirmedResult(tx, matchId, winnerSide)` — победитель и продвижение в одной транзакции. Сначала блокируется жеребьёвка схватки (`FOR UPDATE`, должна быть опубликована), затем схватка: результаты на двух коврах одной сетки продвигаются по очереди и не перезаписывают стороны друг друга, а новая версия жеребьёвки не удалит только что сыгранную схватку. Вызывающий не блокирует схватку до вызова. Стороны зависимых схваток приводятся к состоянию сетки, начатую или сыгранную схватку изменить нельзя (`DEPENDENT_MATCHES_STARTED`). Снятие участника после жеребьёвки пока не меняет сетку: в ней участник помечен «снят», поражение неявкой — Phase 7.
- Сетки видит персонал турнира (`competition.view`); тренерам, спортсменам и зрителям они откроются на публичной странице (Phase 9).
- Коды ошибок `DRAW_ALREADY_PUBLISHED`, `DRAW_NOT_ENOUGH_PARTICIPANTS`, `MATCH_PARTICIPANTS_INCOMPLETE`, `DEPENDENT_MATCHES_STARTED` добавлены в каталог `packages/contracts`; события `draw.published`, `draw.superseded`; действия аудита `draw.created`, `draw.published`, `draw.superseded`, `bracket.advanced`.

### ARCHITECTURE.md

- Модули `draws` (генератор, вход и хеш, посев, BYE, разведение, версии), `brackets` (стратегии форматов, граф, состояние, продвижение, места) и `matches` (владелец таблиц схваток: в 5a — создание, стороны, удаление; машина состояний — Phase 7). Зависимости: `draws → brackets → matches`; категории переводит `CategoryWorkflowService` модуля `categories` (системные переходы `READY_FOR_DRAW ⇄ DRAWN` с аудитом и событием).
- **14.4:** стратегия — `validate`, `build` (граф по размеру жеребьёвки), `dynamic` (правило источника `DYNAMIC`), `placements`. Вместо `onResultConfirmed` состояние сетки — чистая функция `resolve(граф, жеребьёвка, подтверждённые исходы)`, а стороны схваток приводятся к ней сравнением: так же работают BYE при публикации, продвижение, утешительные схватки и (в Phase 7) изменение результата.
- **14.5:** состояние xoshiro128** — сами 128 бит seed (без хеширования), чтобы повтор мог проверить кто угодно; разведение — штраф пары `4^(K − круг встречи)`, ключи сравниваются по приоритету; сначала расставляются самые большие команды, затем попарные обмены, пока они уменьшают штраф (предел — 64 прохода). Штраф позиции считается по числу участников группы в блоках сетки — за O(K); 256 участников расставляются примерно за 0,5 с. Отчёт: для каждой группы — лучший возможный и фактический круг первой встречи. В круговой системе разведение не применяется, посеянные получают номер жеребьёвки, равный номеру посева.
- **Места** (правило согласуется с главным судьёй до Phase 7): олимпийская система — 1, 2, 3, 3, далее по кругу выбывания (5, 9, …); выбывание с утешительными — 1, 2, два 3-х (победители утешительных), проигравшие последней утешительной — 5-е, предыдущей — 7-е и т. д.; участники утешительных выше проигравших в основной сетке не финалистам, те — по кругу выбывания; круговая система — победы, затем победы во встречах между собой (рекурсивно), затем чистые победы и победы по преимуществу, иначе место делится.

### ARCHITECTURE.md

- **Подписчики outbox в транзакции** (`OutboxService.subscribe`): проекции, которые меняются вместе с причиной. Допуск пересчитывается по событиям решений и переводов участий, объединения категорий, требований положения, документов (`document.status_changed`) и согласий (`consent.given`, `consent.revoked`) — модули-источники о допуске не знают. - При слиянии дублей спортсмена отметки прибытия и медицинские допуски переходят к основному профилю, допуск пересчитывается (`athlete.merged`).
- Пересчёт пропускает турнир, право записи которого у площадочного узла: облачные данные (документы, согласия) не меняют операционные таблицы, пока пишет узел (ADR-21, Phase 9.5).
- Уведомления создаёт worker (очередь `notifications`): получатели по событию, доставка в ленту сразу, письмо — отдельной задачей с повторами; тексты писем — в worker, тексты ленты — в словарях web, подстановки — общая функция `notificationSource` в `packages/db`.

### API.md

- **Публичный API** — `/api/public/v1/competitions` и `/{slug}` вне префикса `/api/v1`, лимит 120 в минуту на IP, `Cache-Control: public, max-age=60, stale-while-revalidate=300`. Ответы собираются по белому списку полей (ADR-15): участники не раскрываются, в категориях — только число одобренных участий. Черновики и удалённые турниры — `404`.
- `GET /competitions` + `mine=true` (турниры с моей служебной ролью, включая черновики) и `registrationOpen=true`. **Опубликованный турнир видит любой вошедший** (иначе клуб не найдёт турнир, чтобы подать заявку); черновик — только с `competition.view`.
- `POST /competitions`: создатель становится `TOURNAMENT_MANAGER`, **кроме создания через платформенную роль** — как с организациями в 0.2.1, администратор платформы не получает прав турнира неявно. Вместе с турниром создаётся право записи облака.
- `POST /competitions/{id}/transitions` + `confirm` и `registrationEndsAt`. Условия с предупреждением (например, «есть нерассмотренные заявки» при переходе в `CHECK_IN`) возвращают `TRANSITION_PRECONDITIONS_NOT_MET` с `details.warnings`; повтор с `confirm: true` выполняет переход. Повторное открытие регистрации требует причины и нового срока окончания в будущем. Закрытие регистрации по сроку выполняет worker (`closeRegistrations`, каждые 5 минут) от имени системы.
- `PATCH /competitions/{id}` после публикации: изменение сроков требует `reason` и порождает `competition.dates_changed`; дисциплина, версия правил и `slug` — `TRANSITION_PRECONDITIONS_NOT_MET` (`published_*_locked`).
- **Персонал:** `POST /competitions/{id}/members` принимает `email` (приглашение письмом) или `userId`; себе роль назначить и свою роль изменить нельзя (`FORBIDDEN`, `self_assignment`) — разделение обязанностей. Добавлен `POST /competition-invites/accept` (`{ token }`).
- **Категории:** название сгенерированной категории — «Юноши 12–14 лет, до 35 кг»: пол, границы возраста группы и вес (название группы в справочнике может уже содержать пол); переименовать можно правкой категории. Добавлены `GET /competitions/{id}/categories/{cId}` и `DELETE` (только категория без участий и только до мандатной комиссии). Переход `CLOSED → REGISTRATION` (при повторном открытии регистрации) требует причины. Объединение — только категорий одного пола и одной политики возраста; спортсмен, заявленный сразу в несколько объединяемых категорий, блокирует объединение (`athlete_in_several_categories`).
- `PUT /team-standing-rule` перенесён в Phase 9 (вместе с командным зачётом): правило без расчёта нечем проверить.
- **Заявки:** `eligible-categories` принимает `declaredWeightGrams` и возвращает `athlete` и `weightMatch` у категорий (вес не делает категорию несовместимой — решает взвешивание). Первое решение персонала по участию переводит заявку `SUBMITTED → UNDER_REVIEW`. Повторная подача после возврата возвращает отклонённые участия в `PENDING`, если спортсмен не заявлен в ту же категорию заново. `CONSENT_MISSING` — нет действующего согласия на обработку ПДн (`PD_PROCESSING`) при добавлении участия; требования турнира к согласиям проверяет допуск (4b).
- Добавлены `POST /entries/{id}/refresh-snapshot` (владелец до подачи), `GET /me/applications` (кабинет клуба и тренера), `GET /athletes/{id}/entries` (карточка спортсмена и выбор турнира при загрузке документа).
- Документы, принадлежащие заявке (`owner.applicationId`), по-прежнему `not_supported`: в 4a документы загружаются на спортсмена с выбором турнира.
- CSV участников: `;`, UTF-8 с BOM, CRLF, защита от формул (ячейка, начинающаяся с `=`, `+`, `-`, `@`, табуляции или перевода строки, начинается с апострофа); выгрузка пишется в аудит (`entry.exported`).
- **Право записи [L]:** guard `WriteAuthorityGuard` проверяет держателя до обработчика, сервис повторяет проверку в транзакции команды. Автотест проходит по всем командам турнира и требует `409 WRITE_AUTHORITY_ELSEWHERE`, когда право у узла.

### API.md

- **ETag — токен конкурентности, а не валидатор кэша** (уточнение 1.4). Производные поля ресурса (статус согласий, представители, `allowedActions`) меняются без смены версии, поэтому `If-None-Match: "v{n}"` не даёт `304`, а ответы API по умолчанию `Cache-Control: no-store` (персональные данные). Справочники — как раньше: `public, max-age=3600` и ETag содержимого.
- `GET /athletes` + `mine=true` — только спортсмены, у которых пользователь — действующий тренер. Спортсмены чужого клуба — `404` (не `403`): пользователь не вправе знать о них.

Тот же родитель второго ребёнка — та же запись «человек».
- **Согласия:** бумажное согласие несовершеннолетнего подписывает подтверждённый представитель — `guardianId` в `ConsentCreate`; за совершеннолетнего — он сам. Повтор действующего согласия — `ALREADY_EXISTS`. Добавлены `GET /admin/consent-templates` и `PATCH /admin/consent-templates/{id}` (только черновик).
- **Тренеры:** `POST /coaches/{id}/end-membership` (`{ organizationId }`); `CoachCreate.confirmNotDuplicate`; `userId` — действующий участник организации с заполненными данными (`not_member`, `person_required`). **Судьи:** реестр общий для организаций — ведёт любой с `referee.manage` (федерация, платформа); `confirmNotDuplicate`.

- **Правила:** добавлены `GET /rulesets/{id}` и `GET /rulesets/{id}/versions/{v}`; новая версия — из `parameters` или копией `basedOnVersion`. Ошибки параметров — `RULESET_PARAMETERS_INVALID` с путями полей.

- **Документы:** проверка — только в контексте турнира (`competitionId` документа). Удаление — только загрузившим и только в `UPLOADED`. Скачивание по `fileId` подчиняется правам документа.
- `Idempotency-Key` обязателен на `POST /athletes/imports`; механизм общий (декоратор `@Idempotent()`), ответ хранится 24 часа.

### PERMISSIONS.md

- **Неактивная организация.** Участники организации на проверке могут только менять её данные и состав (`organization.update`, `organization.members.view`, `organization.members.manage`) без наследования на дочерние и на турниры. Приостановленная или архивная организация даёт только `organization.members.view`. Иначе создатель «федерации на проверке» мог бы одобрять дочерние организации.
- **Создатель с полномочиями не становится руководителем** (0.2.1). Иначе `PLATFORM_ADMIN` или `FEDERATION_ADMIN`, создав клуб, получали бы права `CLUB_MANAGER` (спортсмены, документы, заявки), которых нет в их ролях. Приглашение первого руководителя при создании не проверяется правилом «роль не шире своей»: это равносильно одобрению самостоятельной регистрации, которое у создателя уже есть.
- **Платформенные роли действуют только при включённом TOTP.** Без него `SUPER_ADMIN` и `PLATFORM_ADMIN` не дают прав.
- **«Роль не шире своей»** сравнивается с правами выдающего в организации и на её турнирах. Поэтому `PLATFORM_ADMIN` не выдаёт организационные роли с правами, которых у него нет (например, `CLUB_MANAGER`); это может `SUPER_ADMIN` или руководитель организации.
- Автотест маршрутов различает три объявления: `@Public`, `@Authenticated`, `@RequirePermission`. Проверка «каждое permission используется маршрутом» включается по мере появления маршрутов (Phase 3–9).

### ARCHITECTURE.md

- Добавлен пакет `packages/server-kit` — общий серверный код api и worker (окружение, криптография, пароли, логирование).
- Порядок guards: `AuthGuard` (только определяет пользователя) → `RateLimitGuard` → `CsrfGuard` → `PermissionGuard` (отказ `401` / `403` / `404`). Так лимит API считается по пользователю, а публичный маршрут работает и с просроченным токеном.
- Письма — только через outbox (`email.requested`) → worker; обработчик идемпотентен (`ProcessedEvent`).
- Prisma Client генерируется в `packages/db/generated` — так его забирает `pnpm deploy` в Docker-образы.
- **Версии зависимостей.** Взяты последние выпуски проверенных мажорных версий: TypeScript 5.9, NestJS 11, Prisma 6, Next.js 15, ESLint 9, Vitest 3. Уже вышли TypeScript 7, NestJS 12, Prisma 7+, Next.js 16 — переход планируется отдельной задачей с проверкой на всём наборе тестов, не внутри функциональной фазы.
