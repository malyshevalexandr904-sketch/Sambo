# Нагрузочный тест живых данных (Phase 8b)

Дата: 2026-10-14, версия 0.11.0 (ветка `phase-8b-notifications`). Цели — PROJECT_ANALYSIS, 7.12: **10 000 зрителей табло** и пиковый поток судейских событий с **12 ковров**. Как запускать — [loadtest/README.md](../loadtest/README.md).

## Итог

- **10 000 зрителей и 12 ковров выдерживаются с запасом при реальном темпе судейства.** При 2 событиях в секунду на все 12 ковров (в 1,5–2 раза выше реального пика) сообщение доходит до зрителя за **118 мс** (медиана), **162 мс** (p95), **216 мс** (p99); команда судьи — 27 мс (медиана). api занят на 19 % одного ядра, PostgreSQL — на 2 %.
- **Потерь нет** ни в одном прогоне: пропусков номеров сообщений — 0, разрывов соединений — 0, отказов подключения — 0 (10 000 из 10 000).
- **Запас одного процесса api:** до 5 000 сообщений зрителям в секунду api занят на 43–58 % ядра; команд — 30–36 в секунду на ядро (27–38 мс процессора на команду). При 12 событиях в секунду и 10 000 зрителях (в 6–10 раз выше реального пика) стенд не справился: задержка — 1 с (медиана), 1,9 с (p95), но насыщено и второе ядро (k6, PostgreSQL и Redis — ≈ 96 %), поэтому точный предел api выше 5 000 сообщений/с на этом стенде не измерить.
- **`NOTIFY` на commit не влияет:** поток команд с триггером `sync_log_notify` и без — одинаковое время ответа (28,0 и 28,3 мс медиана при 12 командах/с) и одинаковая загрузка. Ограничение ARCHITECTURE.md, 13 («commit с `NOTIFY` сериализуется») на этих объёмах не проявляется; узкое место — процессор api на саму команду (27–38 мс одного ядра на оценку), а не база.
- **Сервер заказчика (1 vCPU / 2 ГБ)** по пропорции: пилот (3 ковра, сотни зрителей) — с большим запасом; 10 000 зрителей при реальном темпе — по процессору проходит (≈30 % ядра вместе с TLS в Caddy), но по памяти на пределе (≈1,7–1,9 ГБ из 2 ГБ). **Для турниров с тысячами зрителей — 2 vCPU / 4 ГБ.**

## Стенд

- Песочница: 2 vCPU Intel Xeon 2,8 ГГц, 8 ГБ, Linux; PostgreSQL 16, Redis 7, Node.js 22; api — production-сборка (`dist`), `LOG_LEVEL=warn`, ограничение частоты запросов выключено (планшеты стенда — с одного адреса).
- **api — одно ядро (как на сервере), всё остальное — второе** (`taskset`): PostgreSQL, Redis и генератор нагрузки k6. Первый прогон без закрепления показал, что k6 с 10 000 соединений забирает 150 % процессора и api голодает (p95 — 6 с) — цифры такого прогона говорят о генераторе, а не о системе.
- Турнир на 12 ковров через API (сетки, расписание, бригады), на каждом ковре — идущая схватка. **Свежий стенд и перезапуск api перед каждым прогоном**: каждая команда пересчитывает состояние схватки по её журналу, и журнал в сотни событий (в настоящей схватке — десятки) удваивал время команды в повторных прогонах.
- Зрители: k6, 200 соединений Socket.IO на VU (`SOCKETS_PER_VU=200`, так запускает `loadtest/run.sh`), каждое подписано на табло своего ковра (`public:mat:{slug}:{n}`, поровну на 12 ковров); подключение — 90 с до начала событий (R4 — 60 с), затем 120 с событий. Задержку меряет каждый десятый зритель (1000 измерителей), сообщения и пропуски считают все.
- Планшеты: 12 VU, по одному на ковёр, оценка 1 балл попеременно сторонам (схватка не заканчивается); событие ковра `m` номер `k` — в момент `T0 + m·PERIOD/12 + k·PERIOD`, зритель по сумме баллов вычисляет момент отправки. Опоздание отправки планшета — медиана ≤ 1 мс (кроме насыщенного прогона R3).
- Ресурсы — каждые 2 с из `/proc` (среднее за окно событий).

## Зрители табло

| Прогон | Зрители | Событий/с (12 ковров) | Сообщений зрителям/с | Задержка p50 / p95 / p99 | Команда p50 / p95 | CPU api | PostgreSQL | Redis | k6 | Память api (макс.) |
|---|---|---|---|---|---|---|---|---|---|---|
| R1 | 10 000 | 2 | 1 670 | 118 / 162 / 216 мс | 27 / 46 мс | 19 % | 2 % | 0 % | 22 % | 465 МБ |
| R2 | 10 000 | 6 | 5 000 | 137 / 517 / 632 мс | 34 / 403 мс | 43 % | 5 % | 1 % | 52 % | 580 МБ |
| R3 | 10 000 | 12 | 9 900 | 997 / 1 890 / 2 540 мс | 790 / 1 460 мс | 75 % (второе ядро насыщено) | 10 % | 1 % | 85 % | 900 МБ |
| R4 | 5 000 | 12 | 5 000 | 131 / 305 / 395 мс | 53 / 230 мс | 58 % | 9 % | 1 % | 46 % | 632 МБ |

- Задержки — **оценка сверху**: генератор k6 работал на одном ядре с PostgreSQL и Redis (столбец «k6» — его загрузка того же ядра), в зале зрители — отдельные устройства.
- **Доставка.** R1, R2, R4: получено ровно столько сообщений, сколько событий × зрителей ковра (200 834, 600 834, 600 417). R3: на 1,2 % меньше при нуле пропусков номеров — планшеты, отставая от расписания (ответ на команду до 1,5 с), отправляли события подряд, и два события ковра попадали в одну пачку ленты (40 мс) — зритель получал одно сообщение с итоговым счётом. Это объединение, а не потеря: табло показывает верное состояние.
- **Хвост задержки** растёт с размером комнаты: R2 и R4 рассылают по 5 000 сообщений в секунду, но при 833 зрителях на ковёр (R2) p95 — 517 мс, при 417 (R4) — 305 мс. Рассылка в большую комнату — непрерывный участок работы цикла событий Node.js, команды и следующие рассылки ждут его.
- **Память:** ≈ 20–35 КБ на соединение в api (≈ 250 МБ без зрителей → 465–580 МБ с 10 000 при 2–6 событиях/с; при насыщении R3 — до 900 МБ: копятся неотправленные сообщения).
- **Объём:** сообщение табло — ≈ 1,5 КБ (полное состояние ковра). 10 000 зрителей при 2 событиях/с — ≈ 2,5 МБ/с (≈ 20 Мбит/с) исходящего трафика, при 12 событиях/с — ≈ 120 Мбит/с (больше типового канала VPS 100 Мбит/с).
- Подключение: 10 000 соединений за 45 с — медиана 0,6 мс, p99 ≤ 21 мс; отказов нет.

## Команды и `NOTIFY`

Только планшеты, без зрителей, 60 с, свежий стенд; «без NOTIFY» — триггер `sync_log_notify` выключен (`ALTER TABLE … DISABLE TRIGGER`), лента изменений молчит.

| Прогон | Команд/с | Команда p50 / p95 / p99 | CPU api | PostgreSQL |
|---|---|---|---|---|
| N1, с NOTIFY | 12 | 28,0 / 46,2 / 62,6 мс | 46 % | 8 % |
| N1, без NOTIFY | 12 | 28,3 / 46,3 / 61,0 мс | 45 % | 9 % |
| N2, с NOTIFY | 40 (цель) → 36 | 91 / 269 / 328 мс | 98 % | 20 % |
| N2, без NOTIFY | 40 (цель) → 36 | 154 / 331 / 430 мс | 98 % | 19 % |

- При 12 командах/с разницы нет. При 40 командах/с api насыщен в обоих случаях (98 % ядра), и разница — шум насыщения (без `NOTIFY` даже медленнее). Commit с `NOTIFY` не стал узким местом.
- Узкое место — процессор api на саму команду: 27–38 мс одного ядра на оценку (N2: 98 % ядра при 36 командах/с; N1: 46 % при 12 — с фоновой работой узла) — проверка входа, права, разбор, пересчёт состояния по журналу, запись события, `sync_log`, аудит. По профилю основная часть — клиент Prisma (подготовка запросов и разбор ответов) и сборка мусора. Это 30–36 команд в секунду на ядро; реальный пик 12 ковров — 1–2 события в секунду.

## Реальный темп и сервер заказчика

- На ковре за схватку 3–5 минут — 10–20 событий (оценки, наказания, секундомер, удержания, вызов и результат): **12 ковров дают 1–2 события в секунду в пике**. Прогон R1 (2 события/с) — этот темп с запасом; R2 и R3 — в 3 и 6 раз выше.
- Сервер заказчика — 1 vCPU / 2 ГБ, на нём же PostgreSQL, Redis, web, worker, MinIO, Caddy (TLS). Оценка по пропорции для 10 000 зрителей при 2 событиях/с: api 19 % + PostgreSQL 2 % + Caddy (TLS 20 Мбит/с, 10 000 соединений) ≈ 5–10 % → **≈ 30 % ядра — проходит**; память: api ≈ 470 МБ + Caddy ≈ 250–400 МБ на соединения + PostgreSQL ≈ 300 МБ + web, worker, MinIO ≈ 450 МБ → **≈ 1,7–1,9 ГБ из 2 ГБ — на пределе**. Пилот (Q-09: 3 ковра, до 150 спортсменов, сотни зрителей) — с большим запасом на текущем сервере.

## Рекомендации

1. **Пилот** — текущий сервер достаточен.
2. **Турниры с тысячами зрителей** — 2 vCPU / 4 ГБ (или PostgreSQL и MinIO на managed-сервисах, Q-07). Один процесс api держит 10 000 зрителей при реальном темпе; запас по пику — несколько процессов api за Caddy (`/ws` с балансировкой): шлюз уже рассчитан на несколько узлов (каждый узел раздаёт сообщения из Redis своим зрителям, ведущий — один).
3. **Трафик** при больших аудиториях — сжатие WebSocket (`perMessageDeflate`) или сообщения-разницы вместо полного состояния ковра (≈ 1,5 КБ) — в Phase 9 вместе с публичными страницами зрителей.
4. **Стоимость команды** (27–38 мс процессора) — профилирование и сокращение запросов на команду, пересчёт по сохранённому состоянию вместо журнала — когда понадобится больше 30 команд/с на ядро (площадочный узел Phase 9.5 с 12 коврами — проверить там же).
5. Ограничение «commit с `NOTIFY` сериализуется» (docs/README.md, Phase 8a) — до 36 команд/с не проявляется; одно уведомление на транзакцию или чтение `sync_log` по номеру — не нужны.
